# Comment in the ticket when closing it after a merge fails

## Context

A PR body line `closes: <ISSUE>` (written by the `/ask-for-review` command and the
`baltech-git` skill of the claude-marketplace plugin) is acted on by the
`closing-issues` job in `.github/workflows/release-actions.yml`: after the merge it
runs `youtrack.py close-issue`, which sets the State to `Closed (Done)`.

YouTrack can refuse that state change, e.g. a workflow rule blocks it while checklist
items ("todo" boxes) in the ticket are unticked. The job deliberately ignores the
failure (`|| echo "::error::could not close $ISSUE"`) - the PR is merged and stays
merged. The only trace is an annotation in a workflow run nobody looks at, so the
author assumes the ticket is closed and the open todos are forgotten.

The fix belongs in ci-scripts, not in the plugin: the plugin only writes the
`closes:` line, and its YouTrack access is read-only by design (writes are blocked by
the plugin's own PreToolUse hook). ci-scripts does the close, holds a YouTrack token
with write access, and is the only place that sees YouTrack's answer.

## Does YouTrack tell the reason?

Yes, but only the rule's fixed message. A real refusal from the `closing-issues` job
(MobileIDManager PR #240, ticket MID-584, 2026-10-13,
https://github.com/baltech-ag/MobileIDManager/actions/runs/38381489546):

```
request `https://youtrack.baltech.de/api/issues/MID-584` failed with status code 400:
{"error":"Assertion failed","error_description":"Resolve all subtasks and checklist items first",
 "error_rule_name":"resolved-guard/restrict","error_issue_id":"3-8921","error_issue_id_readable":"MID-584",
 "error_issue_is_draft":false,"error_workflow_type":"assert","error_workflow_rule_path":"","error_type":"workflow"}
```

- `error_description` carries the human-readable reason. It tells what to do
  ("resolve all subtasks and checklist items"), but not *which* items are open.
- `error` is only "Assertion failed"; `error_rule_name` names the blocking rule.

`youtrack.py` already prints that body in `_fail()` (since cf57b19a), it is just never
shown to anybody. The comment takes `error_description`, then `error`, then the raw
body, and shows it verbatim.

This was the only refusal with a logged body since 2026-03-17 across ToolSuite,
PythonSW, Bros2FW, BaltechSDK, MobileIDManager, MobileIDApp and MobileMaintainer.
TS-563 and SDK-198 (March 2026) also got a 400, from the older `/api/commands` code
that did not log the body.

## Changes

### 1. `youtrack.py` - `close-issue` can comment on a refused close

- Extract the request of `set_state()` into `_set_state_request(issue, state)`;
  `set_state()` keeps its behaviour (`set-state` subcommand, `review-issues` job).
- `close_issue()` gets two optional parameters:
  - `comment_on_failure` (CLI flag `--comment-on-failure`): when the state change
    answers with an HTTP error, add a comment to the issue, then fail exactly as
    before (exit 1 with the request error, so the workflow annotation stays).
  - `pr_url` (CLI `--pr-url`): the merged PR, linked from the comment.
- New helpers:
  - `_error_reason(body)` - the human-readable part of a YouTrack error body.
  - `_close_failed_comment(issue, state, reason, pr_url)` - the comment text.
- A 404 (issue does not exist) needs no extra handling: `add_comment()` already
  skips it with a warning.
- Without the flag nothing changes - `issue-close` (the composite action) and
  `close-issue` keep failing loudly as before.

Comment (English and HTML-in-markdown, like the other CI comments in YouTrack;
the reason is HTML-escaped, line breaks become `<br>`):

```
⚠️ Closing this ticket failed. The pull request <url> with `closes: XX-123`
was merged, but YouTrack refused to set the state to Closed (Done):
    > <reason from YouTrack>
The ticket stays open: resolve the reason above, then close it by hand.
```

YouTrack notifies the ticket's watchers about the new comment, so the people who
work on the ticket see it without opening any workflow run.

### 2. `.github/workflows/release-actions.yml` - job `closing-issues`

Pass `--comment-on-failure --pr-url="$PR_URL"` to `close-issue`, with
`PR_URL: ${{ github.event.pull_request.html_url }}` in the step's `env`. The
`|| echo "::error::could not close $ISSUE"` stays: the job still does not fail.

No template change: the callers use `release-actions.yml@master` and
`ci-scripts-ref` defaults to `master`, so the change is live once merged.

## Notes / non-goals

- The `review-issues` job (`In Review`) is unchanged; a refused `In Review` is not
  worth a comment.
- No retry and no state check after the fact (e.g. in `/ask-for-review`): the
  comment is written at the moment the close fails, where the reason is known.
- A failure that is not an HTTP answer (network error) gets no comment - there is
  no YouTrack to write it to.
- The comment does not list the open subtasks / checklist items itself (decided by
  the user): they are already in the ticket, so a list would be redundant. The
  comment is only a pointer to what is left to do.

## Verification

No test suite in this repo. Run `youtrack.py close-issue --comment-on-failure`
against a local fake YouTrack (`http.server`) that answers the state change with the
real MID-584 400 body (plus a line with markup), and check:
- the comment POST arrives with the escaped reason and the PR link,
- the exit code is 1 and stderr carries the original request error,
- without `--comment-on-failure` no comment is sent,
- a successful close sends no comment and exits 0.
